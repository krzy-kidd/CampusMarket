# CAMPUS TRADE — MASTER DEVELOPMENT PROMPT

## 1. PROJECT OVERVIEW

Develop a secure, reliable, student-exclusive online marketplace named **campusTrade** for Western Mindanao State University (WMSU).

The platform allows verified WMSU students to buy and sell items within the university community.

The system must prioritize:
- Student verification and account security.
- Simple buying and selling.
- Reliable transaction management.
- Secure private messaging.
- Fair cancellation and dispute resolution.
- Protection of student information.
- A responsive, user-friendly interface.
- Maintainable and scalable application architecture.

**IMPORTANT: This platform is strictly for BUYING AND SELLING.**

Do not implement:
- Item trading or exchanging.
- Trade offers.
- Counteroffers.
- Price negotiation features.
- Offer management.
- Any trade-related database tables, API endpoints, frontend components, or business logic.

All listings must have a fixed selling price.

# 4. STUDENT REGISTRATION AND ANNUAL COR VERIFICATION

Student verification must happen once every academic year, not every semester.

### Verification process

1. Student creates an account.
2. Student verifies their WMSU email address.
3. Student submits their current academic year's Certificate of Registration (COR).
4. The submission receives Pending Review status.
5. A Verification Admin reviews the document.
6. The admin approves or rejects the submission.
7. If rejected, the student receives the rejection reason and may submit a corrected document.
8. Once approved, the student receives a Verified status and badge.
9. When a new academic year begins, students must submit a new COR.
10. Restricted marketplace actions remain unavailable until the new verification is approved.

### Important verification rules

- Verification is tied to the currently active academic year.
- Previous verification records must be preserved.
- A student must not receive permanent verification from an old COR.
- Only one approved verification record per student per academic year is allowed.
- Only the Super Admin can configure the active academic year.
- If no academic year is configured, the system must not automatically grant verified access.
- Email verification and academic verification must be separate account conditions.

### COR document security

- Store COR files in private Laravel storage.
- Do not expose public COR URLs.
- Only the document owner and authorized administrators may access the file.
- Use authenticated document preview and download endpoints.
- Validate file extension, actual MIME type, file content, and size.
- Generate randomized filenames.
- Reject executable or suspicious files.
- Apply malware scanning where available.
- Do not expose internal storage paths in API responses or logs.
- Establish a document retention and deletion policy.

### Listing rules

- Every listing must have a fixed price.
- Sellers cannot create trade-only listings.

- Sellers may edit their listings while doing so does not conflict with an active transaction.
- Price changes must not alter an already-created transaction's agreed-price snapshot.
- Listings must not be deleted in a way that destroys transaction history.
- Administrators may remove prohibited or reported listings.

### Listing statuses

Use these listing statuses:

1. Available — The product is available for purchase.
2. Pending Agreement — A buyer has initiated a purchase and the parties are coordinating.
3. Locked / Meetup Arranged — Both parties have agreed to proceed and confirmed a meetup arrangement. Other buyers cannot purchase the item.
4. Sold — The transaction has been successfully completed.
5. Archived — The seller or an authorized administrator has removed the listing from active marketplace display.

Do not use the old Reserved status.

# 7. BUYING AND SELLING TRANSACTION PROCESS

The transaction system must follow a clear, fair, and reliable process.

## Step 1: Buyer discovers a product

The buyer browses available listings and checks:
- Product description.
- Price.
- Condition.
- Photos.
- Seller profile.
- Seller rating.
- Verified student badge.

## Step 2: Buyer clicks Buy Now

The buyer selects Buy Now and confirms their intention to purchase.

The backend checks:
- Buyer account is active and academically verified.
- Listing exists.
- Listing is Available.
- Buyer is not the seller.
- No conflicting active transaction exists.
- The listing has not already been claimed by another valid purchase process.

The system creates a transaction with a snapshot of the current listing price.

## Step 3: Pending Agreement

After the purchase request is created, the transaction receives Pending Agreement status.

The listing changes to Pending Agreement.

At this stage:
- The buyer and seller communicate through a private conversation.
- They discuss the proposed meetup.
- They agree on a date, time, and campus location.
- The listing remains available to other eligible buyers until both parties confirm the meetup arrangement.

If another buyer successfully initiates a valid purchase before the first transaction reaches the locked stage, the backend must apply the First Come, First Served rule and prevent conflicting transactions.

## Step 4: Both parties confirm the meetup

The buyer and seller must independently confirm the meetup arrangement.

The meetup arrangement should record:
- Agreed date.
- Agreed time.
- Agreed campus location.
- Buyer confirmation.
- Seller confirmation.

Only after both parties confirm must the system:
- Change the transaction status to Meetup Arranged.
- Change the listing status to Locked / Meetup Arranged.
- Prevent other buyers from purchasing the item.
- Notify both parties.

The backend must perform this transition atomically.

A buyer clicking Buy Now alone must never lock the listing.

## Step 5: Face-to-face meetup

The buyer and seller meet at their agreed campus location.

The buyer may inspect the product before completing the purchase.

Payment and product handover happen directly between the buyer and seller.

The platform does not process or hold payments.

The platform does not provide shipping or delivery services.

## Step 6: Successful transaction

After the buyer receives the item and the seller receives payment:

- The buyer confirms completion.
- The seller confirms completion.
- Both confirmations are recorded independently.
- The system changes the transaction status to Completed.
- The listing changes to Sold.
- Both parties receive notifications.
- Both parties become eligible to review each other.

Neither participant should be able to confirm completion on behalf of the other.

A transaction must never become Completed based on only one confirmation.

# 8. FAILED MEETUP, CANCELLATION, AND LISTING UNLOCKING RULES

This section is especially important. Implement the following process exactly.

The system must protect both buyers and sellers when an agreed meetup does not happen.

## A. Both parties agree that the meetup failed

If the buyer and seller both agree that the meetup did not happen or that they cannot proceed:

1. Either party selects Cancel Transaction / Report Failed Meetup.
2. The other party receives a notification.
3. The other party confirms the cancellation.
4. The system automatically changes the transaction status to Cancelled.
5. The system changes the listing status back to Available.
6. The item becomes purchasable by other eligible students again.
7. The system records the cancellation reason and transaction event.
8. Both parties receive notifications.

## B. Seller requests to make the listing available again

If the meetup fails and the buyer does not respond or confirm cancellation:

1. The seller may submit a Request to Unlock Listing.
2. The system notifies the buyer.
3. The buyer receives a reasonable response period to confirm cancellation or report a legitimate issue.
4. The response period must be configurable by the Super Admin.
5. Use a default response period of 24 hours unless the Super Admin changes it.
6. If the buyer does not respond within the configured period, the system may automatically cancel the transaction and return the listing to Available.
7. Record the seller's request, buyer notification, response deadline, and final action in the transaction history.

The system must not automatically unlock listings simply because the scheduled meetup time has passed.

The 24-hour response period applies only after a seller has formally requested to unlock a listing. It is not a general reservation expiration timer.

## C. Buyer disputes the cancellation

If the buyer reports a legitimate reason for not attending or disputes the seller's request:

- Keep the transaction locked.
- Change the transaction status to Disputed.
- Notify administrators.
- Allow both parties to submit explanations and supporting evidence.
- Require Admin Mediation.
- Do not automatically mark the item Sold or Available while the dispute is unresolved.

## D. Admin mediation

An authorized administrator may:
- Review transaction history.
- Review meetup details.
- Review messages and submitted evidence where authorized.
- Request additional information.
- Resolve the dispute.
- Cancel the transaction and return the listing to Available.
- Apply appropriate account restrictions if misconduct is established.

All administrative decisions must be recorded in the audit log.

## E. Additional cancellation rules

- Cancellation must require a reason.
- Only authorized participants or administrators may initiate the relevant cancellation actions.
- A completed transaction cannot be cancelled through the normal cancellation process.
- Disputed transactions cannot be automatically unlocked.
- Repeated cancellation abuse may be flagged for administrative review.
- Never erase transaction history when a transaction is cancelled.
- Do not automatically unlock a listing without a valid cancellation or authorized resolution.

# 9. TRANSACTION STATUS AND LISTING STATUS MUST BE SEPARATE

Do not use a single status field for both listings and transactions.

### Listing status

- available
- pending_agreement
- locked
- sold
- archived

### Transaction status

- pending_agreement
- meetup_arranged
- completed
- cancelled
- disputed

The backend must enforce valid state transitions.

Example:

Listing:
Available → Pending Agreement → Locked → Sold

Alternative:
Available → Pending Agreement → Locked → Available

Transaction:
Pending Agreement → Meetup Arranged → Completed

Alternative:
Pending Agreement → Cancelled

Alternative:
Meetup Arranged → Cancelled

Alternative:
Meetup Arranged → Disputed → Cancelled or other authorized resolution

A disputed transaction must remain locked until it is resolved.

The system must not allow invalid transitions, such as:
- Cancelled → Completed.
- Completed → Cancelled.
- Sold → Available without an authorized correction process.
- Disputed → Available without resolution.
- Locked → Sold without both completion confirmations.

# 10. FIRST COME, FIRST SERVED AND CONCURRENCY PROTECTION

The platform must support First Come, First Served purchasing.

The first valid purchase process to successfully complete the backend's required checks and database operation receives priority.

Requirements:

- Use database transactions.
- Use row-level locking where supported.
- Lock the listing record during critical purchase and state transitions.
- Prevent multiple active transactions for the same listing.
- Use database constraints where appropriate.
- Use idempotency protection for purchase requests.
- Prevent duplicate requests caused by repeated clicks or network retries.
- Return a clear error if another buyer has already claimed the listing.
- Never trust frontend availability checks alone.

Only one active transaction may exist for a listing at a time.
